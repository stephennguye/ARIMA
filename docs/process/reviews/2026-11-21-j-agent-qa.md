BLOCKERS (must fix before continuing)
1. `roles.ts:174` (`npm test` / `npm run` / `npm ci` for qa) together with `Write(./tests/**)` – QA writes the test files and then runs them through npm, so QA can run any code it likes. The guard only ever sees the text `npm run e2e`. A test file can call `child_process` or `fs` to run `git log` / `git show feat/US-n:src/...` / `git show arima-state:...` (a sparse worktree still shares the full object store). It can also read `$ARIMA_PROJECT_DIR/.arima/runs/*.report.json` (run-agent.ts:286 hands QA that path), read `~/.config/arima` (the Notion token file), and send anything out with `fetch`, because there is no network limit when the sandbox is off, and off is the default. The build card admits this for writes only ("advisory via a script run by npm run (R-01)", docs/build/agents/qa.md:94). For reads it says "Enforced by role list and checkout" (:96), which is false. Consequence: the spec 5.8 independence requirement and the §11.3 secret rule are not enforced for QA. A prompt-injected criterion is enough to exfiltrate the Notion token.
2. `qa-tests.ts:73-79,98-121` – The "only tests/" check looks at `git status` of the working tree, never at the commits between the base and `HEAD`. Code started through npm (blocker 1) can commit changes to `src/`, `package.json`, `playwright.config.*` and so on in QA's worktree and leave it clean. The host then takes `HEAD` and runs `branch -f` to move the story branch onto it. No protected-path, secret or attribution check runs on that range: the secret scan covers only the host's own staged diff. Also, the host's `git commit` (:87) runs with the repository's hooks and no `core.hooksPath` override. `.git/hooks` is shared by all worktrees and test code can write to it, so QA can get code run on the host. Consequence: product code or config changed by QA lands on the story branch. The developer's later publish check then counts those changes as the developer's.
3. `dispatch.ts:1149-1150,1253-1275` and `report.ts:146-163` – A QA report with verdict `pass` makes the engine set `Last result: Pass` on every test case of the story, and merge depends on that value. Nothing checks that `npm run e2e` ran, that it exited 0, that every case was run, or that `criteria_map` is all `met`. A `pass` with `unmet` criteria is accepted. Evidence is only shape-checked: `NEW-1`, any `path:line` (including `src/x.ts:3`) and any `tests/.evidence/...` path pass without checking that the file exists. Consequence: a hallucinated or injected pass sets test cases to Pass that never ran, which the card itself forbids (agents/qa.md:52).

MAJOR (fix in this stage)
1. `proposals.ts:24-38` – The "reproduced in two runs" rule trusts the `reproductions` number that QA writes into its own record. No host-side count of failing runs exists. S1/S2 findings in `report.findings` are never lowered, and those findings are posted to the PR (dispatch.ts:1128). Outbox entries imported from a sandbox clone (sandbox.ts:479) skip `bugSeverityRule` entirely. The card's claim "the engine accepts S1 or S2 only when the failure reproduced in two runs" (build card :112) is therefore not true.
2. `hooks.ts:670,938-947` – `Glob` and `Grep` are granted unscoped (`roles.ts:170-171`). The guard checks only the `path`/`glob`/`pattern` strings for a literal `src|docs|.arima|.github|.git` segment. A Grep with no `path`, a Glob of `**/*.js`, or patterns like `sr[c]/**`, `s?c/**` or `{src,x}/**` all pass. In the default sparse worktree those files are not on disk. But the sandbox clone (`sandbox.ts:228-256`) is a plain, **non-sparse** clone of the QA branch, and nothing re-applies QA_SPARSE there, so `src/` and `docs/` exist in `/work`. So WP-190, which the card names as the fix for R-01, takes away the sparse-checkout control. The clone also keeps objects from all refs after `remote remove`. The card's claim that reads are "path-scoped" for Glob and Grep (build card :46, :88) is false.
3. `publish.ts:206-214,236-249` – `git diff --name-only` uses rename detection by default, so a rename shows only the destination path. If the developer moves `tests/e2e/a.spec.ts` to `tests/unit/a.spec.ts`, QA's test disappears and the e2e rule sees no `tests/e2e/` path. Fix with `--no-renames`. The QA-only-tests rule in publish and the grader's `--diff-filter=D` have the same blind spot.
4. Weakening QA's tests without touching `tests/e2e/` – The developer may freely edit `playwright.config.*` (testDir, testIgnore, grep, retries), the `e2e` script in `package.json`, and shared helpers or fixtures under `tests/` outside `e2e/` that QA's tests import. publish.ts and hooks.ts protect only the `tests/e2e/` prefix. When no `qa/…-tests` branch exists, QA runs the story branch's `package.json` (dispatch.ts:619-622). That is developer-authored code running inside QA, which breaks the judge rule "no role runs code from another role".
5. `qa-tips.json` (`qa-tests.ts:35`) is the only basis for `testsBase`. The developer can also run code through npm (developer has NPM_TEST plus Write everywhere) and can rewrite `$ARIMA_PROJECT_DIR/.arima/state/qa-tips.json` to its own latest commit. That hides its own `tests/e2e` edits from the publish check (publish.ts:233-247). The file guard does not cover processes started by npm.
6. `QA_SPARSE` (dispatch-units.ts:71) is `tests/ api/ design/ package.json`. It leaves out `package-lock.json`, `playwright.config.*` and `tsconfig*.json`, which QA_READS and the agent file promise. `npm ci` refuses to run without a lockfile, and a fresh worktree has no `node_modules`. The evals use `node --test` with no dependencies and their own sparse set (scenarios.real.eval.ts:91), so they never exercise this. Unconfirmed: whether a production QA run can execute `npm run e2e` at all.
7. Graders and scenarios accept wrong runs:
   - Successful `Read`/`Glob`/`Grep` calls are never logged, because post-tool-use logs only write tools, WebFetch and non-read-only Bash (hooks.ts:1175-1180). `no-forbidden-attempt` therefore only sees *blocked* reads. Scenario 8 runs on a full tree, where a Grep with no path reads `src/cart.js` unnoticed, and it passes as long as the report does not repeat the note's words.
   - No grader or scenario checks that `npm run e2e` actually ran before a verdict. Scenarios 4 and 8 pass a run that guessed `pass` from the test file.
   - `WEAK_TEST` scans added lines only. In kind qa, deleting an `assert` from an existing test, or adding `expect(1).toBe(1)`, `test.fixme`, `toBeTruthy()` on a constant, or a try/catch that swallows failures, all pass.
   - `bugProblems` accepts the text "tests/e2e" anywhere as evidence. It does not check that the bug matches a failing test, that the evidence file exists, or that `reproductions >= 2` for S1/S2.
   - Only test-write has a real "can this test fail?" check (good/bad/baseline servers).
8. `adoptQaTests` is called only for test-write. Bug evidence under `tests/.evidence/` in kind qa stays in a worktree that the next run deletes (dispatch.ts:612). A bug's `Actual` points at a file that will not exist later.

- Protection of the e2e runner's config and script, and of the helpers QA's tests depend on, against the developer.
