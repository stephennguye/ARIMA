Branch `feat/wp-213-devops-env` (stacked on `feat/wp-190-docker-sandbox` and PR #17, none merged). Status of the package: **built and tested, verified live on real Docker and with a real `claude -p`; stays open** for protocol steps 7 (real-agent evals with thresholds) and 8 (judge), see the end.

## 1. Live check on real Docker (Docker Desktop, daemon running)

A scratch app repo (git, `arima.yaml` with `staging.url` on port 3299, an `infra/compose.yaml` with one service built from the local `postgres:17-alpine` image running a netcat HTTP server, one named volume). Run through the built bundle `plugins/arima/scripts/dist/arima-env.mjs`.

| Step | Result |
| --- | --- |
| `check` | design check passes, `docker compose config` ok |
| `up staging` (v1) | built, started, healthy, smoke 200 on `127.0.0.1:3299/healthz`; state and `deploy.staging` event written |
| `up staging` (v2, a version that answers 500 and fails its health check) | exit 71; `the previous version is running again`; v1 still answers 200; the failed attempt is in the event log (`ok: false, restored: true`) and the recorded staging is still v1 |
| `backup staging` | one archive per named volume, written next to the repository (`<repo>-backups/staging/`), containers read-only and `--network none` |
| `restore-test staging` | latest archive restored into a throwaway volume, files present, throwaway volume removed (none left) |
| `up preview-5 --ref main` | port 4100 (first of the range), healthy, smoke 200 |
| `down preview-5`, `down staging` | containers gone; the preview's volume removed, the **staging volume kept** (as designed) |
| `up production`, `down Production` | `refused`, exit 70, nothing ran |

**Bugs the live run found that the fake Docker could not:** (a) `--project-directory` was the repository root, so `build: ..` in `infra/compose.yaml` resolved outside the repository; it must be the Compose file's own folder (fixed, with a test); (b) the toy image first used `busybox httpd`, which the postgres image does not ship (test fixture only). Everything created was removed afterwards (volumes, `arima-local/*` images, the pulled `alpine:3.20`, the scratch repo and backups).

## 3. Mutation checks

Twelve mutants, applied one at a time to `env.ts` and `compose-lint.ts`, each run against `env.test.ts` and `compose-lint.test.ts`: accept `production` as staging; pass the whole process environment to Docker; skip the rollback; drop the kill-switch check from `up`; `down staging --volumes`; never evict a preview; do not refuse a production-naming Compose file; ignore a mismatching `compose_project`; do not withhold secret-looking log lines; drop the `privileged` rule; drop the Docker-socket rule; drop the `prod` token. **All 12 were killed.** (One mutant first did not match its text because of formatting; it was re-run by hand and killed.)

## 4. What else changed, and why

- `roles.ts`, `hooks.ts`: ADR-0008 (devops has no `docker` at all), `guardContainers`, the whole `~/.config/arima/` folder is a secret path (the old rule only covered the Notion token file; the per-project production env file lives there).
- `dispatch.ts`: a unit with item `none` no longer calls `branchFor` (it threw for any such unit, the CI-red `fix` included, before the worktree check).
- `queue.ts`: the failing-staging unit is `deploy-staging`, as the card says (it was `fix`).
- `evals/v0.1/init.eval.ts`: an old test broken by WP-104 (outbox entries must belong to a run the engine started, and `ba` may not write gates) was repaired: it now starts the run and uses the orchestrator. Found because `npm run eval` was not among the handoff checks.
- ADR-0008 written as **Proposed**; the owner is asked to confirm it.

## 7. Independent attack on the production barrier

A fresh read-only agent (briefed with the goal and the files, none of my conclusions) ran its repros against the code and found **3 blockers, 5 major, 4 minor** (repros kept for the session in `tmp/judge/`, not committed). Each was reproduced by the attacker; after the fixes its own repros were run again. Answers:

| # | Finding | Answer |
| --- | --- | --- |
| B1 | `git fetch --upload-pack=<cmd>` runs a host command and passes the guard and the allow-list | **Fixed.** The guard refuses any option on `git fetch`, `pull`, `ls-remote`, `clone` in a role run. Tests in `devops-envelope.test.ts` |
| B2 | `npm test`, `npm run`, `npm ci` with `--prefix infra` run scripts from `infra/package.json`, which devops can write | **Fixed twice.** devops no longer has `npm run` or `npm ci` (only `npm test`, `outdated`, `audit`, `sbom`); the guard refuses `--prefix`, `-C`, `--workspace(s)`, `-w`, `--script-shell`, `--userconfig`, `--globalconfig`, `--cache` for every role |
| B3 | A volume source of `${HOME}` passes the lint and `HOME` is in the Docker environment: the host home, with the production env files, could be mounted | **Fixed.** New rule `interpolation`: no `$VAR` or `${VAR}` other than exactly `${ARIMA_*}` anywhere in the file, except under `environment`, `command`, `entrypoint`, `labels`, `healthcheck`, `args`. The `.config/arima` pattern now tolerates repeated slashes |
| M1 | `build.dockerfile` was not linted, and a build error printed the first line of an arbitrary host file | **Fixed.** `dockerfile` must be relative and inside the repository. Every build, compose and git error text that looks like a secret is withheld whole (messages, state, events) |
| M2 | `check --file <any path>` reads any file and echoes the YAML parser excerpt | **Fixed.** `--file` must resolve (links followed) inside the project, else exit 70; a syntax error reports only the line number |
| M3 | Guard secret-path rules missed globs and `//` (`~/.config/ar?ma`, Grep on `~/.config` with a glob) | **Fixed.** Any glob after `.config/` in a role command, and any Read, Grep or Glob field naming `.config`, is refused |
| M4 | Lint evasions: `privileged: yes`, `volumes_from`, `container:` links, `external_links`, explicit names, `driver_opts`, `0.0.0.0::80`, `cgroup`, `sysctls`, extra capabilities, `seccomp=<path>`, `provider`, interpolated paths | **Fixed**, moving the lint from a deny-list towards an allow-list: `privileged` only a literal `false`; `cap_add` only `NET_BIND_SERVICE`, `CHOWN`, `SETUID`, `SETGID`, `KILL`; no `container:` link, `volumes_from`, `external_links`; `container_name` and explicit volume or network names must start with `${ARIMA_PROJECT}`; no volume drivers, `cgroup`, `sysctls`, `provider`; every published port on loopback; `host` compared case-insensitively; no `secrets.environment` |
| M5 | `--project <dir>` is unrestricted | **Fixed in the guard.** A role may not pass `--project` or `--file`, a glob or `..` to `arima-env` (the host and a human may) |
| minor | `--run-id` was free text in the event log; stderr unredacted in state and events; a file name inside `sh -c` text; a one-letter volume name read as a drive | `--run-id` must match `r-YYYYMMDD-HHMM-NN`; redacted as in M1; the archive name is now an argument; the one-letter name stays flagged (a false positive on the safe side) |
| suspicion | symbolic links in the repository pass the textual "inside the repo" check | **Fixed.** A deployed ref that holds a symbolic link is refused with exit 70 before any build |
| suspicion | `down`, `status`, `logs` ran Compose in the project folder and so parsed a root `compose.yaml` or `.env` | **Fixed.** They run in an empty temp folder (they address the project by name) |

What held, in the attacker's report: strict target parsing, the project key schema and the `compose_project` equality, the scrubbed Docker environment (no Notion or GitHub token reaches Compose), `--ref` values that look like options, the scope of `down --volumes`, label-scoped backup and restore, the state-file schema, and direct `docker`, `gh`, `git push`, `$()` and wrapper forms in the guard.

Still allowed after the fixes and judged acceptable: `git show --no-index`, `git log --ext-diff` (they need configuration a devops run cannot write), `arima-env up preview-5 --ref staging` (a ref name, harmless), `npm run` for the other roles (their own lists, not devops), and a model-written `node -e` (in no allow-list; the sandbox, WP-190, is the control for that).

Lesson for the next role that gets such tools: **an allow-list that lets a role write files must never also let it run something that executes files it can write** (npm scripts, git options and hooks, a Compose build).
