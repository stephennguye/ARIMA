BLOCKERS (must fix before continuing)
1. `publish.ts:184-210` together with `roles.ts:144-145` (`git switch`, `git checkout`) and `hooks.ts:301-376` (`guardGit` has no case for `checkout` or `switch`). The final check before publishing compares `${defaultBranch}...${branch}` against the **local** `main` ref. A developer can move that ref with allowed commands and the guard does not stop it. The sequence: commit a forbidden change (for example tests/e2e restored to an older version, or a `.github/workflows` file written by an `npm run` script). Then run `git checkout -B main --ignore-other-worktrees`. Then go back to the feature branch and add a normal feature commit. The merge-base is now the forbidden commit, so the protected-path and tests/e2e checks see only the feature commit. The host still pushes the whole branch. Consequence: the card's last line of defence ("caught at publish") is bypassable. A workflow file pushed this way runs on `pull_request` with repository secrets before any human approval. It also breaks spec §5.7 "must not touch `main`". Fix: compare against `origin/<default>` (or a sha the host records before the run), block `-B/-C/--force/--ignore-other-worktrees` and any switch to the default or state branch for roles, and add tests.
2. `hooks.ts:575` (the state-read rule only matches the literal text `.arima`) together with `roles.ts:32-41` (`git show *`, `git log *`, `git diff *` are allowed) and `state.ts:146-186` (`.arima/` is a git worktree of the `arima-state` branch in the same repository). The files on the state branch sit at its root with no `.arima/` prefix. So `git show arima-state:runs/<id>.report.json`, `git log -p arima-state` and `git diff main arima-state` all pass both the permission list and the guard. Consequence: a developer can read ARIMA state, including other roles' run reports, the mirror and the events log. That breaks card §3 ("reads neither the mirror nor run reports"). The same route is open to tech-lead, which shares `GIT_READ`, and that defeats the independence in spec §5.8. With `git checkout --ignore-other-worktrees arima-state` followed by `git commit`, a developer might even **write** to the state branch (not traced further). Fix: in the guard, refuse any git ref or revision argument that names the state branch, `--all`, or `refs/`. Add a test for each spelling.
3. `hooks.ts:543-556` (`guardQaTests`) disagrees with card §6, which says "Enforced for … direct shell commands". The rule only fires when the text `tests/e2e` appears. These allowed commands change QA's tests without it: `git checkout HEAD~3 -- tests`, `git checkout HEAD~3 -- .`, `git checkout HEAD~3 -- ':(glob)tests/*2e/**'`, `git checkout <other-branch>`, followed by `git add -A` and `git commit -am`. Consequence: what the card claims is enforced is not. Only the publish check stops these, and blocker 1 bypasses that.

MAJOR (fix in this stage)
1. `report.ts:66-143` and `dispatch.ts:938`. A report with `status: done` passes even when criteria are `unmet` or `unclear`, or when an acceptance criterion is missing from `criteria_map` (the code checks only that the list is non-empty). `publishDevelop` then opens the PR. Card §5 says "every `met` has evidence that exists in the diff or tests", but no production code checks this. The schema accepts any non-empty string as evidence (for example "see code"), and only the eval grader resolves `file:line`. Consequence: a run can claim criteria are met without evidence and still be accepted and published.
2. `report.ts:129-136`. `needs_input` is accepted with no question at all, or with only non-blocking ones. Only `blocked` requires a blocking question. Questions can also be downgraded to `findings` or to non-blocking questions while the run still reports `done`. Consequence: questions can be hidden, and the item sits idle with a run recorded as a pass. There is also a conflicting instruction: `outputContractFor` (`dispatch-units.ts:129`) says "Ask a question only for a hard-stop matter or a critical blocker; decide everything else", while the card's step 2 requires a blocking question for any ambiguous criterion.
3. `hooks.ts:297`. Hook skipping is blocked only for the exact `--no-verify` and for `-n`. Git also accepts unambiguous shortened forms of long options, such as `git commit --no-veri -m x` (behaviour assumed, not run). That would skip the commit hook, which is the hook enforcing D-48 attribution rules. The grader's `FORBIDDEN_COMMAND` regex misses it too.
4. Card §6 forbidden-actions table overstates what is enforced:
   - "Push … Guard enforced": the guard only sees the command text. A package.json script run with `npm run x` can still call `git push`, using the host's git credential helper or SSH key, because `HOME`, `APPDATA` and `XDG_RUNTIME_DIR` are passed through (`run-agent.ts:177-228`). WP-111 removes only the token in the environment, not these credentials.
   - "Run … any command outside the list: Enforced": `npm run`, `npm test` and `npm ci` run any package.json or lifecycle script, and the developer can edit package.json because Write is unscoped.
   - "Weaken QA e2e tests … CI runs QA's tests unchanged": `playwright.config.*` and the `test:e2e` script are outside `tests/e2e` and are not protected anywhere. Editing them skips QA's tests while publish, the guard and the grader all stay green.

   R-01 names some of this, but each row should say "advisory via scripts" and give the scenario.
5. `roles.ts:139-140` (bare `Edit` and `Write`) and `hooks.ts` (no rule confining paths to the worktree). Spec §5.7 says "Read/Edit/Write inside its worktree". F09 relies on "confinement by working directory", which nobody has tested in `dontAsk` mode with a bare allow rule. If writes outside the worktree are allowed, then `Write ~/.gitconfig` (`core.hooksPath`) is not covered by `isSecretPath` or `isProtectedConfigPath`. It would plant a hook that runs inside the host publish script's `git push`, and that process has `GH_TOKEN` in its environment (`publish.ts:137`). Sibling worktrees at `../<repo>-wt/*` are also neither read- nor write-protected by the guard.
6. `evals/developer/graders.ts` lets wrong runs pass:
   - **Skipped or deleted test:** `tests-pass` runs the package.json `test` script, which the developer may edit (`onlyUnder` includes `package.json`). `.skip` or `{ skip: true }` passes. Deleting a test passes too, and scenario 1's "test added" check even counts a deletion as an addition. Only scenario 3 checks for one specific file.
   - **Push attempt:** the regex `git\s+(-\S+\s+)*push` misses `git -C . push` and `git -c k=v push`. A push from inside a script is invisible. `describe()` (`hooks.ts:903`) drops the whole command when it looks like a secret, which skips every command check. The card's grader "no remote ref changed" is not built, and the scratch repo has no remote. `denials` are reported only if some other problem is found (`scenarios.real.eval.ts:109`).
   - **Forbidden path:** `--exclude-standard` hides writes to gitignored paths. Writes outside the repo are not looked at. Commits on another branch (for example local `main`) are invisible to `base..HEAD` and to the working-tree diff.
   - **Blocked status:** scenarios 2 and 7 accept `blocked` and exit code 3 although the card expects `needs_input`. This is minor, and done on purpose.
7. `roles.ts:147` grants WebFetch to any host, and `git fetch <url>` is allowed (`hooks.ts:450-457` blocks only options). Spec §5.7 "Tools" lists no web access, and no ADR covers it. The packet's `web.hosts: []` allow-list is not enforced. This is an exfiltration channel and a deviation from the spec without an ADR.

MINOR / NOTES
- Card §3 and the agent file say the developer must not read `.github/`, `arima.yaml`, `team.yaml` or other worktrees. Only writes are blocked; the guard allows these reads.
- The guard and `deniedTools` match paths without regard to case, but `publish.ts:204` uses a case-sensitive `startsWith('tests/e2e/')`. With git's default `core.quotePath`, non-ASCII names come out quoted (`"tests/e2e/\303…"`) and slip past that check.
- `git commit --amend` is allowed, but the agent file says "may not … rewrite history".
- Card §12 says "Turn caps 40 / 60 / 80", while §9 and `TURN_CAPS` say 30/50/80.
- The `CLAUDE_*` environment variables are passed through, so scripts the agent writes can read `CLAUDE_CODE_OAUTH_TOKEN`. The guard blocks only `$…TOKEN` in command text.
- Windows 8.3 short names (for example `ARIMA~1`) are not normalised by `canon()`. Low risk.
- `developer-envelope.test.ts` has no case for MultiEdit, NotebookEdit, a Read/Glob/Grep under `.arima`, `git checkout <ref> -- tests`, or the state branch.
